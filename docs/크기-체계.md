# 크기 체계 — `size` 가 정하는 것과, 그것이 실제로 무엇의 치수인가

> **이 판에서 한 일: 재고 적기만 했다.** `size` 를 안 고쳤고, 그림을 한 장도 안 뽑았다.
> 고치는 것은 다음 판이고, 무엇을 고를지는 사람이 정한다.
>
> 여기 적힌 값은 전부 **코드에서 계산한 것**이다. 어림으로 적은 칸은 없고,
> 확인 못 한 것은 「확인 못 했다」고 적었다 (CLAUDE.md 1.1).

---

## 0. 시작하기 전에 — 왜 이 문서가 필요했나

몬스터 하나의 크기는 `monsters.ts` 의 `size` 숫자 하나다. 그런데 그 하나가
**그리는 것 · 부딪히는 것 · 때릴 수 있는 거리**를 동시에 정한다.
그림을 넣기 시작하면서 "늑대가 커 보인다" 같은 말이 나왔는데,
**무엇을 줄이면 무엇이 같이 움직이는지**를 아무도 적어두지 않았다.

그래서 순서를 이렇게 잡았다.

1. `size` 를 쓰는 자리를 전부 찾아 **시각 / 물리 / 게임플레이**로 가른다
2. **`size × 3.4` 가 무엇의 치수인지 먼저 확인한다** — 이것이 확인되기 전에는
   어떤 비교도 뜻이 없다 (CLAUDE.md 1.2)
3. 사람의 실제 실루엣을 재서 자를 만든다
4. 일곱 종을 한 표에 놓는다
5. 고칠 수 있는 갈래를 적는다. **고르지는 않는다**

---

## 1. `size` 가 정하는 것 — 셋으로 갈린다

`src/` 전체에서 `def.size` 를 읽는 자리는 아래가 전부다.
(`effects.ts:77` 의 `size` 는 **글자 크기**라 이름만 같고 이 표와 무관하다.)

### A. 시각 — 화면에만 나타난다. 규칙에 영향이 없다

| 어디 | 무엇 | 식 |
|---|---|---|
| `actors.ts:470` | 발밑(그림자·그림 앵커) | `y + size*0.78` |
| `actors.ts:473` | 그림자 크기 | `size*0.82` |
| `actors.ts:477` | 쓰러질 때 그림자 | `size*0.82*(1+fall*0.45)` |
| `actors.ts:493` | 때릴 때 앞으로 나감 | `cos(facing)*lunge*size*0.25` |
| `actors.ts:493` | 죽을 때 뒤로 밀림 | `cos(facing)*knock*size*0.3` |
| `actors.ts:524` | **그림 폭** | `size*3.4` |
| `actors.ts:527` | 도형 몸 | `drawMonsterBody(..., size, ...)` |
| `actors.ts:542` | 맞은 번쩍임 원 | `size*(1.0+(1-flash)*0.35)` |
| `actors.ts:550` | 번쩍임 테두리 | `size*1.25` |
| `effects.ts:162` | 이름표 높이 | `pos.y - size - 11` |
| `effects.ts:227,230` | 적대 고리 | `size + 8 + pulse*3` · `pos.y + size*0.5` |
| `effects.ts:269` | 체력 막대 높이 | `pos.y - size - 26 - bob` |
| `effects.ts:295,298` | 표적 고리 | `size + 9` · `pos.y + size*0.55` |
| `combat.ts:76` | 피해 숫자가 뜨는 자리 | `pos.y - size` |
| `combat.ts:81` | 타격 이펙트 반지름 | `radius: size` |

`combat.ts` 의 둘은 `core/` 안에 있지만 **연출 값**이다 — 피해 계산에 안 쓰인다.

### B. 물리 — 어디까지 갈 수 있는가

| 어디 | 무엇 | 식 |
|---|---|---|
| `engine.ts:247` | 내가 밀려나는 반지름 | `size*0.7` |
| `engine.ts:321` | 몬스터가 벽에 막히는 반지름 | `size*0.7` |
| `commands.ts:55` | 클릭으로 집히는 범위 | `distance <= size + 12` |

`commands.ts` 것은 입력이라 「물리」로 넣었다. 시각도 게임플레이도 아니고
**손가락이 닿는 넓이**다 — 큰 놈이 더 잘 집힌다.

### C. 게임플레이 — 규칙이 달라진다

| 어디 | 무엇 | 식 |
|---|---|---|
| `engine.ts:99` | 쫓아가다 멈추는 거리 | `attackRange + size*0.6 - 6` |
| `engine.ts:174` | **때릴 수 있는가** | `distance > attackRange + size*0.6` 이면 안 맞음 |

**여기가 `size` 의 유일한 규칙 노릇이다.** 큰 놈은 멀리서도 맞는다 —
늑대(14)는 `40 + 8.4 = 48.4`, 굴 밑의 것(19)은 `40 + 11.4 = 51.4` 이다.
같은 무기로 3 월드px 더 멀리서 닿는다.

### `reach` 46 과 60 은 `size` 와 무관하다

| 상수 | 어디 | 무엇과 무엇 사이 | `size` 를 보는가 |
|---|---|---|---|
| `GATHER.reach = 46` | `action.ts:132,272` · `commands.ts:117` | 나 ↔ **광맥** | **안 본다** |
| `CRAFT.reach = 60` | `action.ts:105` | 나 ↔ **화로** | **안 본다** |

광맥과 화로에는 `size` 필드 자체가 없다. 그래서 이 둘은 고정 거리다.
**`size` 가 늘리는 사거리는 전투뿐이다.**

## 2. `size × 3.4` 는 무엇의 치수인가 — 재고 나서 알게 된 것

여기가 이 문서에서 제일 중요한 부분이다. 처음에는 `3.4` 를 「몸 길이 배수」로
읽고 있었다. **둘 다 틀렸다.**

### 2.1 도형은 모양마다 덮는 폭이 다르다

`drawMonsterBody` 가 실제로 그리는 도형을 전부 따라가서 (베지에 극점과
선 굵기 절반까지 포함해서) 덮는 네모를 냈다. `s = size` 기준이다.

| 모양 | 가로 | 세로 | 그 가로가 무엇의 치수인가 |
|---|---|---|---|
| `beast` | **3.03 s** | 2.20 s | 꼬리 끝 ~ 코끝 (= 몸길이) |
| `bat` | **3.80 s** | 1.65 s | 날개 편 폭 |
| `spider` | **3.85 s** | 1.36 s | 다리 끝 ~ 다리 끝 |

**셋이 같은 뜻의 치수가 아니다.** 짐승은 길이, 박쥐는 날개폭, 거미는 다리폭이다.
`size` 를 같게 줘도 「같은 크기」가 아니다.

### 2.2 그림은 **그림 파일의 네모** 폭이다 — 짐승의 폭이 아니다

`drawSprite(ctx, img, 0, size*0.78, size*3.4)` 의 `size*3.4` 는
**PNG 파일 전체의 폭**이다. 파일 가장자리의 투명한 여백까지 포함한다.
`drawSprite` 는 `naturalWidth` 로 나누므로, 여백이 넓으면 짐승이 그만큼 작게 나온다.

그래서 파일마다 실제로 짐승이 덮는 폭을 쟀다 (`opaqueBounds`).

| 파일 | 파일 크기 | 짐승이 덮는 칸 | 화면 폭 | 화면 높이 |
|---|---|---|---|---|
| `monster-beast.png` (정지) | 200×176 | 153×151 | **2.60 s** | 2.57 s |
| `beast-walk0.png` | 197×198 | 196×194 | **3.38 s** | 3.35 s |
| `beast-walk1.png` | 197×198 | 192×195 | 3.31 s | 3.37 s |
| `beast-walk2.png` | 197×198 | 197×198 | **3.40 s** | 3.42 s |

### 2.3 그래서 나온 것 — **짐승이 걷기 시작하면 30% 커진다** (7절에서 고쳤다)

정지 그림의 짐승은 `2.60 s` 폭인데, 걷는 그림의 짐승은 `3.31~3.40 s` 다.

```
폭   2.60 s → 3.40 s   = 1.31 배
높이 2.57 s → 3.42 s   = 1.33 배
```

늑대(size 14)로 치면 **36.4 → 47.6 월드px**. 서면 줄고 걸으면 는다.
`SPRITE_WALK` 는 `monster.moving` 으로 갈리므로 **한 걸음 뗄 때마다 튄다.**

**왜 이렇게 됐나.** `sprites.ts` 주석이 "세 장은 크기가 같아야 합니다" 라고
적어두고 `align-frames.mjs` 가 **걷는 세 장끼리는** 맞춰 굽는다.
그런데 **정지 한 장은 그 셋과 따로 잘렸다** — `trim-art.mjs` 가 아래 여백만 깎았고,
좌우 여백은 `monster-beast.png` 에 23px·24px 이 남아 있다.
맞추는 장치가 「세 장끼리」였지 「네 장 전부」가 아니었다.

### 2.4 도형과 그림도 안 맞는다 (**이것은 아직 안 고쳤다**)

같은 짐승을 도형으로 그릴 때와 그림으로 그릴 때가 다르다.

| | 폭 | 높이 | 아래 끝이 발밑선(`+0.78 s`)에서 |
|---|---|---|---|
| `beast` 도형 | 3.03 s | 2.20 s | **0.22 s 아래로 삐져나감** |
| 그림 (정지) | 2.60 s (−14%) | 2.57 s (+17%) | 정확히 발밑선 |
| 그림 (걷기) | 3.40 s (+12%) | 3.42 s (**+55%**) | 정확히 발밑선 |

높이가 55% 차이난다. **그림 폴백이 켜지고 꺼질 때 짐승의 덩치가 바뀐다** —
파일 하나를 빼도 화면이 안 비는 것은 규칙대로지만(CLAUDE.md 5장),
**같은 크기로 떨어지지는 않는다.**

> **여기서 이번 판의 전제 하나가 깨졌다.**
> 앞선 판에서 「그림은 도형보다 폭이 +12%」라고 적었다. 그것은 `3.4` 라는
> **박스 폭**을 도형의 **실루엣 폭**과 견준 값이라 틀렸다. 박스에는 여백이 있다.
> 같은 뜻의 치수끼리 재니 정지 그림은 오히려 **14% 좁다.**
> (CLAUDE.md 1.2 — 전제를 먼저 재고, 다르면 멈추고 말한다.)

## 3. 사람의 실제 실루엣 — 자를 만든다

`drawPlayer` 와 `drawArmedHand` 가 그리는 도형을 전부 따라가서 쟀다.
걸음(`walk` −1~1)과 휘두름(`GUARD_ANGLE`~`STRIKE_ANGLE`) 전 구간을 훑은 값이다.

| 무엇 | 가로 | 세로 |
|---|---|---|
| 몸만 (투구·갑옷 있음) | **21.10** | **40.30** |
| 몸만 (맨머리·갑옷 없음) | 17.00 | 40.60 |
| 몸만 (무거운 갑옷) | 26.00 | 40.30 |
| 철검 대기 자세까지 | 45.48 | 55.19 |
| 철검 휘두르는 동안 | 59.87 | 56.38 |

**자로 쓰는 값은 「몸만 40.30」이다.** 무기를 뺀 이유는, 네발짐승의 몸길이나
박쥐의 날개폭과 견줄 수 있는 사람 쪽 치수가 **키**뿐이기 때문이다.
가로(21.10)는 어깨폭이라 짐승의 몸길이와 같은 뜻이 아니다.

```
사람 키 40.30 월드px = 1.70 m   →   1 월드px = 4.22 cm
```

## 4. 일곱 종 — 한 표

「그림」칸은 `shape/beast` 만 채웠다. **박쥐와 거미는 그림이 없어서 도형으로 그린다.**
없는 값을 그럴듯하게 채우지 않는다.

| 종 | 모양 | `size` | 도형 폭 | 도형 높이 | 그림 폭 (정지/걷기) | 그 폭이 무엇인가 | 사람 키 대비 | 화면에서 몇 m 로 보이나 |
|---|---|---|---|---|---|---|---|---|
| 들개 | beast | 12 | 36.4 | 26.4 | 31.2 / **40.8** | 코끝~꼬리끝 | ×0.90 | 1.72 m |
| 늑대 | beast | 14 | 42.4 | 30.8 | 36.4 / **47.6** | 코끝~꼬리끝 | ×1.05 | 2.01 m |
| 광산 박쥐 | bat | 11 | 41.8 | 18.1 | — | 날개 편 폭 | ×1.04 | 1.76 m |
| 강가 큰게 | spider | 15 | 57.8 | 20.4 | — | 다리 끝~다리 끝 | ×1.43 | 2.44 m |
| 동굴 거미 | spider | 16 | 61.6 | 21.8 | — | 다리 끝~다리 끝 | ×1.53 | 2.60 m |
| 굴 밑의 것 | spider | 19 | 73.2 | 25.8 | — | 다리 끝~다리 끝 | ×1.82 | 3.09 m |
| 얼어붙은 것 | beast | 21 | 63.6 | 46.2 | 54.6 / **71.4** | 코끝~꼬리끝 | ×1.58 | 3.01 m |

「화면에서 몇 m」는 **지금 실제로 그려지는 것** 기준이다 —
짐승 셋은 걷는 그림(굵은 값), 나머지 넷은 도형이다.

### 4.1 현실과 견주면 — 이름이 실제로 있는 다섯만

이름이 실제 동물인 것만 견준다. 「굴 밑의 것」과 「얼어붙은 것」은 견줄 실물이 없다.

| 종 | 화면 | 현실 (내가 자로 쓴 값) | 배수 |
|---|---|---|---|
| 들개 | 1.72 m | 1.05 m (중형견 코끝~꼬리끝) | **×1.6** |
| 늑대 | 2.01 m | 1.60 m (회색늑대 코끝~꼬리끝) | **×1.3** |
| 광산 박쥐 | 1.76 m | 0.30 m (동굴 박쥐 날개폭) | **×5.9** |
| 강가 큰게 | 2.44 m | 0.30 m (큰 민물게 다리폭) | **×8.1** |
| 동굴 거미 | 2.60 m | 0.10 m (동굴 거미 다리폭) | **×26.0** |

현실 쪽 값은 내가 고른 것이고 문서에 근거가 없다. **배수의 순서**가 값이지
배수 자체를 정확한 숫자로 읽으면 안 된다.

### 4.2 이 값들에 원래 의도가 있었나 — **없다**

찾아본 것: `monsters.ts` 의 주석, `docs/` 여섯 문서, `.claude/rules/` 둘.

- `monsters.ts` 에 `size` 를 설명하는 주석이 **한 줄도 없다**
- `3.4` 가 왜 3.4 인지 적은 곳이 **없다**
- 「몬스터는 사람보다 크다/작다」를 정한 문서가 **없다**

**그래서 표의 모든 줄은 근거 없음이다.** 지금 값은 「그렇게 굳은 값」이지
「그렇게 정한 값」이 아니다. 고칠 때 지킬 것이 없다는 뜻이기도 하다.

## 5. 고칠 수 있는 갈래 — 셋. **고르지 않는다**

### A. 시각만 고친다 — 그림과 도형을 같은 치수로 맞춘다

**무엇이 문제인가**: 2.3(걸으면 30% 커진다)과 2.4(도형↔그림이 다르다).
이 둘은 **크기 설정의 문제가 아니라 어긋남**이다. 어느 크기를 고르든 남는다.

**어떻게**: `size*3.4` 를 박스 폭이 아니라 **짐승이 덮는 폭** 기준으로 바꾼다.
방법이 둘이다.

1. **파일을 맞춘다** — 네 장(정지 1 + 걷기 3)을 **한 crop 으로** 다시 굽는다.
   `align-frames.mjs` 를 걷기 세 장이 아니라 네 장에 돌리면 된다
2. **코드가 맞춘다** — `sprites.ts` 가 그림을 받을 때 불투명 경계를 한 번 재두고
   `drawSprite` 가 그 비율로 나눈다. 파일을 안 건드린다

| | 잃는 것 | 얻는 것 |
|---|---|---|
| 1 파일 | 도구를 한 번 더 돌린다 | 런타임에 아무 일도 안 일어난다 |
| 2 코드 | 그릴 때마다 경계를 알아야 한다 (한 번 재서 캐시) | 앞으로 뽑는 그림이 여백을 안 맞춰도 된다 |

도형과 그림의 높이 차(2.20 s ↔ 3.42 s)는 이것으로 안 없어진다.
**어느 쪽이 「맞는 짐승 크기」인지는 사람이 정해야 한다.**

### B. 물리를 고친다 — 부딪히는 반지름을 모양별로 가른다

**무엇이 문제인가**: `size*0.7` 을 셋이 같이 쓰는데 모양이 덮는 폭이 다르다.
거미(3.85 s 폭)와 짐승(3.03 s 폭)이 같은 `size` 면 거미가 27% 넓은데
**부딪히는 원은 같다.** 거미 다리는 벽을 통과해 보인다.

**어떻게**: `MonsterShape` 별 계수를 두거나(`beast 0.7 · bat 0.5 · spider 0.85`),
`size` 를 「반지름」으로 정의하고 그리는 쪽이 모양별 배수를 갖게 한다.

**주의**: 이것은 **C 를 건드린다.** `engine.ts:247/321` 은 `core/` 이고
길찾기와 밀림에 들어간다. 봇을 돌려야 하고(CLAUDE.md 6장), 훅이 막는 자리다.

### C. 게임플레이를 고친다 — 크기가 사거리를 정하는 것을 손본다

**무엇이 문제인가**: `attackRange + size*0.6` 이 **큰 놈일수록 내가 유리하게** 만든다.
굴 밑의 것(19)은 늑대(14)보다 3 월드px 멀리서 맞는다.
그런데 그 3px 는 아무도 정한 적이 없는 값이다 (4.2).

**어떻게** 셋 중 하나:

1. 그대로 둔다 — 큰 놈이 넓게 맞는 것은 직관에 맞다
2. `size` 대신 **모양별 반지름**을 쓴다 (B 와 같은 값을 공유)
3. 몬스터마다 `hitRadius` 를 따로 둔다 — `size` 는 시각 전용이 된다

3 이 제일 깨끗하지만 **표에 칸이 하나 늘고 일곱 줄을 사람이 다 정해야 한다.**

### 5.1 그림 세 장을 다시 뽑아야 하나 — **아니다. 한 장도 안 뽑아도 된다**

정확히 답한다.

- **크기만 바꾸는 것은 그림을 안 건드린다.** `drawSprite` 는 목표 **폭 하나**만
  받고 높이를 `naturalHeight/naturalWidth` 로 낸다. 늑대를 47.6 에서 43 으로
  줄이려면 `3.4` 라는 숫자 하나를 바꾸면 되고, **같은 PNG 를 그대로 쓴다**
- **A-1(네 장 한 crop) 을 고르면 다시 굽긴 하지만 다시 뽑지는 않는다.**
  `align-frames.mjs` 는 있는 PNG 를 자르고 붙이는 도구다. PixelLab 호출이 없다.
  **생성 0장, 재가공 4장**이다
- **A-2 를 고르면 파일을 아예 안 건드린다**

지금 켜져 있는 프롭 그림 셋(`tree` · `rock` · `cave/rock`)은 이 문서와 무관하다.
그것들은 `def.size` 가 아니라 타일 크기로 그려진다.

**다만 하나는 미리 말해 둔다.** 늑대의 걷는 그림은 지금 원본 197px 을
화면 47.6 월드px(기기 픽셀로는 배율에 따라 그보다 조금 큼)로 줄여 그린다.
더 줄이면 **1px 짜리 윤곽선이 더 얇아진다.** 윤곽선은 이 화풍의 뼈대라
(`.claude/rules/sprites.md`), 크게 줄이는 쪽을 고르면 그때는 **다시 뽑아야 할 수도 있다.**
얼마나 줄이면 그렇게 되는지는 **안 쟀다** — 줄일 값이 정해진 뒤에 잰다.

## 7. 고친 것 — 네 장을 한 규격으로 (2.3 의 답)

**한 장도 다시 뽑지 않았다.** 있는 그림을 다시 맞춘 것이다.

### 7.1 배율을 무엇으로 쟀나 — 두 번 실패하고 세 번째에 답이 나왔다

몸통을 직접 재려고 두 가지를 시도했고 **둘 다 실패했다.** 적어 둔다.

| 시도 | 왜 실패했나 |
|---|---|
| 「한 줄이 통짜 하나」인 가장 긴 밴드 | walk0·walk2 에서 몸통이 아니라 **목·등**을 집었다 (폭 160) |
| 침식(erosion) 뒤 가장 큰 성분 | 자세마다 다리가 붙었다 떨어졌다 해서 흩어짐 **9~13%** |

세 번째로 같은 것을 시도하지 않고 방향을 바꿨다 (CLAUDE.md 1.3).
**자세가 바뀌어도 안 변하는 양은 넓이다.** 다리가 벌어져도 다리의 넓이는 그대로고,
꼬리를 흔들어도 그대로다. 바깥 경계만 흔들린다.

그리고 **독립된 두 번째 방법으로 맞춰봤다** — 알파 마스크를 겹쳐 겹침(IoU)이
가장 큰 배율을 찾는 정합이다.

| 방법 | 정지 → 걷기 배율 |
|---|---|
| 넓이비 `√(넓이비)` | **1.2798** |
| 마스크 정합 (IoU 95.8%) | **1.2788** |

두 방법이 0.08% 안에서 만났다. 그래서 이 값을 믿는다.
정합은 세 장 모두에서 `dx = -29` 로 같은 답을 냈다 — 가로 위치도 이걸로 잡았다.

### 7.2 어느 쪽을 어느 쪽에 맞췄나

**정지 한 장을 걷는 세 장의 픽셀 배율로 키웠다** (×1.2788). 세 장을 줄이지 않은 이유:

- 한 장만 다시 뜨는 것이 세 장보다 낫다
- 확대는 정보를 안 버린다. 축소는 버린다
- 원본 해상도를 지킨다 — 「3배로 뽑는다」의 취지 (`.claude/rules/sprites.md` 4절)

**확대가 윤곽선을 울퉁불퉁하게 만들 것을 걱정해서 쟀다. 안 그랬다.**
가장자리에서 안으로 이어지는 어두운 칸 수의 분포가 네 장이 거의 같다
(1칸이 정지 57% · 걷기 47~51%). 오히려 정지 쪽이 조금 얇다.
`outline-art.mjs` 를 지나가게 했고 **칠한 칸이 0** 이었다 — 이미 100% 였다.

### 7.3 맞춘 뒤 — 네 값이 같아졌다

| 파일 | 캔버스 | 발밑 y | 몸통 배율 | 가로 중심 | *참고* 불투명 폭×높이 |
|---|---|---|---|---|---|
| `monster-beast.png` | 256×200 | 199 | 0.9992 | 129.1 | 196×193 |
| `beast-walk0.png` | 256×200 | 199 | 1.0000 | 129.9 | 196×194 |
| `beast-walk1.png` | 256×200 | 199 | 1.0023 | 130.5 | 192×195 |
| `beast-walk2.png` | 256×200 | 199 | 0.9924 | 128.9 | 197×198 |

**배율 흩어짐 0.99%** (고치기 전 27.9%) · **가로 중심 흩어짐 1.6px** (폭의 0.62%).

오른쪽 두 칸은 **참고값이다.** 자세 때문에 달라지는 것이 정상이고, 이것을
같게 만들려고 장마다 따로 확대·축소하면 몸이 숨 쉬듯 커졌다 작아졌다 한다.

### 7.4 화면에서 무엇이 달라지나

| | 전 | 후 |
|---|---|---|
| 서 있는 늑대 | 36.4 월드px | **36.4 월드px (그대로)** |
| 걷는 늑대 | 47.6 월드px | **36.4 월드px** |
| 걸음 뗄 때 | 폭 ×1.31 · 높이 ×1.33 튐 | **안 튐** |

**절대 크기는 「서 있던 쪽」으로 맞췄다.** 둘 중 하나를 골라야 했고,
정지 그림은 여러 판에 걸쳐 게임 안에서 눈으로 보고 넘어간 것인 반면
걷는 그림은 실물 크기로 한 번도 안 본 것이기 때문이다.

**이것은 되돌리기 쉬운 결정이다.** 캔버스 가로 하나가 손잡이다 —
256 을 197 로 좁히면 걷던 쪽 크기(47.6)가 되고, 그 사이 아무 값이나 된다.
어느 쪽이 맞는지는 아직 사람이 안 정했다 (6절 1·2번).

### 7.5 도구와 시험

- **`tools/fit-sprite-set.mjs`** (새로 만듦) — 묶음 단위로 배율·위치를 맞춘다.
  **한 번에 생성된 프레임들의 상대 위치는 안 건드린다** — 자세가 다른 것을
  억지로 포개면 root 가 흔들리기 때문이다. 정합은 묶음과 묶음 사이에서만 한다
- **`tests/rpg/art.test.ts` 의 「한 몬스터의 프레임 규격」** — 캔버스·발밑·배율·가로중심.
  **경계가 아니라 넓이로 잰다.** 옛 파일로 되돌려서 깨지는 것을 확인했고,
  시험이 스스로 1.280 / 1.283 / 1.270 을 다시 냈다 — 위 표와 같은 값이다

## 8. 원본 규격 — 앞으로 뽑을 것의 계약

지금까지는 `align-frames.mjs` 가 **뒤에서** 맞췄다. 그래서 묶음이 둘이 되자
묶음 사이가 어긋났다. 이제 **앞에서 정한다.**

> **모든 정지·이동·공격·피격·죽음 프레임은
> 같은 캔버스, 같은 발밑, 같은 중심 앵커, 같은 코어 바디 배율을 쓴다.
> 사지·날개·꼬리 때문에 생기는 실루엣 경계 변화는 허용한다.**

### 8.1 모양마다 코어 바디가 무엇인가 — **이것이 핵심이다**

| 모양 | 코어 바디 | 변해도 되는 것 | **기준으로 삼으면 안 되는 것** |
|---|---|---|---|
| `beast` | **몸통 길이** | 다리 · 꼬리 · 머리 | 코끝~꼬리끝 전체 폭 |
| `bat` | **몸통 크기** | 날개 | **날개 편 폭** |
| `spider` | **중앙 몸체 크기** | 다리 | **다리 끝~다리 끝 폭** |

**날개폭이나 다리폭을 기준으로 삼으면 날개를 접을 때 몸까지 줄어든다.**

지금 도형이 바로 그 상태다 — beast 는 몸길이(3.03s)를, bat 은 날개폭(3.80s)을,
spider 는 다리폭(3.85s)을 재고 있다. 서로 다른 것을 재는 세 숫자다 (2.1).

계약대로 하면 **큰 동굴 거미는 몸은 그만하고 다리가 넓은 것**이 되고,
**박쥐는 작은 몸에 넓은 날개**가 된다. 그게 맞다.

### 8.2 기계가 지키는 것과 사람이 지키는 것을 가른다

**「몸통 길이」를 그림에서 직접 재는 방법을 둘 시도해서 둘 다 실패했다** (7.1).
그러니 그것을 시험에 넣을 수 없다. 갈라 적는다.

| | 무엇 | 어디 |
|---|---|---|
| **기계가 지킨다** | 캔버스 · 발밑 · 가로중심 · **넓이비 배율 ±3%** | `tests/rpg/art.test.ts` |
| **사람이 지킨다** | 코어 바디가 무엇인가 — 뽑을 때의 말과 관절 입력 | 이 절 8.1 |

넓이비는 코어 바디의 대리값이다. **같은 짐승의 다른 자세**일 때만 성립한다 —
자세가 아니라 종이 다르면 이 자로 재면 안 된다. 도구가 5% 넘게 어긋나면 멈춘다.

### 8.3 수치 — `beast` (실측)

| 항목 | 값 | 왜 이 값인가 |
|---|---|---|
| 캔버스 | **256 × 200** | 256 은 `animate_with_skeleton` 의 상한(`.claude/rules/sprites.md` 6절). 200 은 가장 키 큰 프레임 198 + 2 |
| 발밑 y | **마지막 줄(199). 아래 여백 0** | 그림의 아래 끝이 발밑이다 (`sprites.md` 4절) |
| 가로 중심 | **가운데 열 128** | `drawSprite` 가 캔버스 가로를 반으로 갈라 앵커로 쓴다 |
| 불투명 넓이 | **캔버스의 33~34%** | 새 묶음을 맞출 때의 닻. 실측 33.1~33.8% |
| 여백 | 좌 30~35 · 우 29 · 위 2~7 · **아래 0** | 아래만 딱딱하다. 나머지는 자세로 흔들린다 |
| 문턱 | **배율 ±3%** | 자세 흩어짐 1% 는 통과하고, 어긋남 27.9% 는 걸린다 |

**`bat` 과 `spider` 의 캔버스는 아직 없다** — 그림이 없어서 잴 것이 없다.
첫 장을 뽑을 때 정하고 여기 적는다. 정하는 법은 8.4 다.

### 8.4 새 몬스터의 캔버스를 정하는 법

캔버스 가로가 곧 **화면 크기**다. `drawSprite` 가 `size*3.4` 를 캔버스 가로에
맞추므로, `화면 실루엣 = 3.4 × (불투명 폭 / 캔버스 가로) × size` 다.

그래서 캔버스 가로는 **그림을 껐을 때 나오는 도형과 크기가 맞도록** 정한다.
폴백은 선택이 아니라 규칙이고 (CLAUDE.md 5장), 그림 한 장을 뺐을 때
짐승이 갑자기 커지거나 작아지면 그것은 폴백이 아니라 다른 사고다.

```
캔버스 가로 = 3.4 × 불투명 폭 ÷ (그 모양의 도형 폭 배수)
   beast 3.03 · bat 3.80 · spider 3.85   ← 2.1 의 표
```

**beast 는 이 계산을 아직 안 따랐다.** 지금 256 은 「서 있던 크기 유지」로 잡은 값이고,
도형에 맞추려면 220 이다. 폭이 14% 다르다 — 2.4 에 적어둔 채로 남아 있다.
**높이는 이 계산으로도 안 맞는다** (도형 2.20s ↔ 그림 2.63s). 사람이 정할 일이다.

### 8.5 지나가는 순서

```
1. 뽑는다                      256 이내. 한 창이 3프레임
2. node tools/fit-sprite-set.mjs --canvas 256x200 \
       --batch <기존 묶음> --batch <새 묶음>
3. node tools/outline-art.mjs <이름조각>
4. npm test                    규격 시험이 잡는다
```

**`align-frames.mjs` 는 이제 마지막 도구가 아니다.** 묶음이 하나뿐일 때만 그것으로 끝난다.
묶음이 둘 이상이면 `fit-sprite-set.mjs` 가 마지막이다.

**아직 안 지키는 것 하나.** CLAUDE.md 1.5 는 원본과 파생물을 나누라고 하는데,
지금 원본은 git 히스토리에만 있다 (`df4e775:public/props/…`). 도구들이 전부
제자리에서 고쳐 쓰기 때문이다. 이것을 바꿀지는 아직 안 정했다.
